# Import load test — 772 MB and 500 MB fixtures

Fixture: `<fixtures>/tenable-vulns.csv`, 809,494,849 bytes,
425,000 rows, 31 columns, generated by `gen_tenable.py`. Shape detected as
`tenable_vuln`, all 31 fields mapped automatically.

Harness: `upload.sh` drives the chunked-upload REST API exactly as the browser
does (193 slices, 9 s); `api.sh` starts the job; the `vulnhub-cron` container
runs every pass from then on. Nothing here is a special code path — it is the
production import.

## Run 1 — cold, into a 112-asset fleet

| | |
|---|---|
| Rows read | 425,000 |
| Import time | 389.06 s (**1,092 rows/s**) |
| Peak memory | **64.29 MB** (`memory_get_peak_usage(true)`) |
| Passes | 213 |
| Rows skipped / failed | 0 / 0 |
| Content hash | 2.9 s over 772 MB = 262.5 MB/s |
| Created | 25,000 assets, 4,000 vulns, 424,929 findings |

Peak memory is flat at 64 MB against a 772 MB file because the reader streams
and checkpoints every 2,000 rows; the file is never held in memory.

## Run 3 — 500 MB, after raising the upload ceiling

Fixture: `<fixtures>/tenable-500mb.csv`, 524,287,728 bytes,
275,368 records — the 772 MB file truncated on a record boundary. Same harness,
same production code path.

| | |
|---|---|
| Upload | **63 slices, 4 s** (8 MB starting slice) |
| Content hash | 500 MB, folded into the 6.7 s of upload+finish |
| Rows read | 275,368 (estimated 270,831 before reading a row — 1.7% out) |
| Import time | 257.08 s (**1,071 rows/s**) |
| Peak memory | **79.8 MB** |
| Passes | 138 |
| Rows skipped / failed | 0 / 0 |
| Staged file after completion | deleted automatically |

The point of this run was the upload half, not the import half — a 772 MB file
had already been through the streaming reader. What changed:

* **The screen used to say "this server accepts 64 MB in a single request",**
  which reads as a 64 MB cap on the file. It never was one: the per-request
  limit and the largest importable file are different numbers, and the second
  one was already 2 GB. The copy now leads with the real ceiling — the smaller
  of `max_bytes()` and free disk — and explains slicing second.
* **php.ini went from 64 M to 128 M** on `post_max_size` and
  `upload_max_filesize`. Not to raise the file limit, which it does not touch,
  but to give a bigger slice room.
* **The slice is now adaptive.** 8 MB to start, timed, and resized towards a
  ten-second target up to a 32 MB ceiling. A 500 MB file over a fast link is
  63 requests instead of 125; over a slow one the slices shrink so no single
  request runs long enough for a fronting CDN (Cloudflare, say) to abandon it at ~100 s.
* **A failed slice is retried** — four attempts with backoff, each preceded by
  asking `GET upload/status` where the server actually got to. Before this, one
  dropped connection at 90% lost the whole upload; a 500 MB upload over a
  public edge makes that a matter of when, not if.
* **`upload/begin` now refuses a file that will not fit on disk**, with the two
  numbers in the message, instead of failing at the slice that fills the
  volume.

## Run 2 — same file again, interrupted mid-run

Started 06:50:44 UTC, finished 07:03:22 UTC. 425,000 rows, 395.48 s of import
time (1,075 rows/s), peak memory 64.29 MB, 213 passes, 0 skipped, 0 failed.
Wall clock was 758 s because roughly five minutes of that was deliberate
downtime.

### A second import of the same file does not grow the database

The upload's `finish` response flagged the duplicate before the job even ran
(`duplicate: {id: 1, rows: 425000}`), and the run itself created nothing:

| Counter | Run 1 | Run 2 |
|---|---:|---:|
| assets_created | 25,000 | **0** |
| assets_updated | 1 | 25,002 |
| vulns_created | 4,000 | **0** |
| vulns_updated | 4,000 | 15,341 |
| findings_created | 424,929 | **0** |
| findings_updated | 71 | 425,000 |

Row counts either side of run 2 are identical:

```
before   assets 25,112   vulns 4,022   findings 425,289
after    assets 25,112   vulns 4,022   findings 425,289
```

Every row matched an existing record on its fingerprint, so the import is a
true upsert rather than an append.

### A mid-run interruption resumes from the byte offset

At 66.8 % the worker was `kill -9`'d and the `vulnhub-cron` container stopped,
so nothing could restart it — the harshest interruption available short of
pulling power.

```
checkpoint after SIGKILL
  status        running
  byte_offset   540,747,082  (66.8%)
  rows_done     284,000      (= 142 x BATCH_ROWS, a clean batch boundary)
  locked_until  07:00:24
  findings      425,289      (unchanged)
```

`rows_done` landing exactly on a 2,000-row boundary is the point: the batch
that was in flight when the process died was rolled back rather than half
written.

With cron restarted the job stayed frozen at 540,747,082 until the 300 s lease
expired — it refuses to double-run — and the 5-minute sweep then re-armed it.
It resumed from exactly that offset (66.8% -> 74.8% -> 100%) and finished
`done` at 809,494,849 / 809,494,849 with `rows_done` 425,000.

The 772 MB staged upload deleted itself from `wp-content/uploads/` when the job
finished.

## What the load test found

Two defects that only appear at this scale, both fixed:

1. **The cron worker OOM-looped.** `Scheduler::HOOK_VERIFY` and
   `HOOK_AUTOMATION` were named identically to the actions they fire, and
   `Scheduler` listens on its own cron events, so each callback re-entered
   itself through `do_action()` and recursed until PHP ran out of memory — a
   9.6 GB worker the container killed every 60 s. Cron events are now
   `vulnhub_cron_*` and `Scheduler::dispatch()` refuses re-entry. See
   `CORE-API.md` §7.
2. **`VulnHub_Tenable_Verifier::run()` raised a `TypeError` on every cron
   run**, masked until (1) was fixed: `do_action()` with no payload still
   passes an empty string, which will not bind to `int $limit` under
   `strict_types`. Registered with zero accepted args.

After both fixes, every scheduled hook runs in well under a second at ~60 MB
against the loaded fleet:

```
vulnhub_cron_run_automations   peak  59.3 MB   0.01 s   15 queries
vulnhub_cron_verify_closures   peak  61.3 MB   0.13 s  140 queries
vulnhub_housekeeping           peak  57.3 MB   0.98 s   16 queries
vulnhub_daily_snapshot         peak  57.3 MB   0.20 s   33 queries
vulnhub_import_sweep           peak  57.3 MB   0.00 s   12 queries
```

`vulnhub_housekeeping` includes `Repo::recalculate_asset_rollups()` across
25,112 assets and 425,289 findings.

## Harness fixes made along the way

- `dev/loadtest.php` counted `{$wpdb->prefix}vulnhub_vulnerabilities`, which
  does not exist; the table is `vulns` and must be named with `vh_table()`.
- `upload.sh` / `api.sh` scraped the import nonce with
  `grep '"nonce"' | head -1`, which picks up whichever portal section renders
  first and made every request 403 `vulnhub_import_nonce`. They now read both
  nonces out of the `VulnHubImport` config object specifically.

# Portal performance at 425,289 findings

The load test left the box holding real volume, which is the only way to find
this class of bug. Every page was measured over HTTP as a logged-in user.

| Page | Before | After |
|---|---:|---:|
| `/vulnerabilities/` | **35.15 s** | 0.22 s |
| `/vulnhub/` (dashboard) | **11.03 s** | 0.60 s |
| `/tickets/` | 1.81 s | 0.23 s |
| `/exceptions/` | 1.92 s | 0.21 s |
| `/vulnerabilities/?search=OpenSSL` | **23.48 s** | 1.54 s |
| `/vulnerabilities/?search=CVE` | 21.29 s | 0.30 s |
| `/vulnerabilities/?search=appsrv` | 12.73 s | 0.26 s |
| `/assets/`, `/portal-admin/` | 0.06 s | 0.04 s |
| `check-pages.sh` (18 wp-admin screens) | **2 m 01 s** | 8.7 s |

Four changes, in order of what they were worth.

### 1. `Repo::findings()` counted through five joins it did not need

`COUNT(*)` ran over findings joined to assets, vulns, people, teams and
tickets. Nothing filters on people, teams or tickets — they are there for the
display columns — but the count paid for them anyway: **21 s**. The join list
is now built from the filters and ordering that actually reference each table.

### 2. `Repo::findings()` sorted 354,000 fully-joined rows to show 25

**14.5 s**. Now it pages over ids in the narrow query, then hydrates the 25
primary keys it needs with the full join. Two queries instead of one, and the
second is a 0.002 s primary-key lookup.

### 3. Search matched through the join, one row at a time

The joined `LIKE` made the optimiser drive off findings and do two
primary-key lookups per row to evaluate it: **22.5 s** for one word. Searches
now resolve against vulns (4,022 rows) and assets (25,112 rows) first and
match on `f.vuln_id IN (...) OR f.asset_id IN (...)`.

Two things fall out of that:

- If every row of either small table matches, the `OR` is true for every
  finding and the search excludes nothing — searching for `e` matches all
  4,022 vulns. The clause is dropped rather than evaluated: 12.2 s to 0.15 s.
- Results are verified identical to the old query — same totals and the same
  first 25 ids across twelve terms — with one intended difference: the asset
  side now also matches `fqdn`, not just `hostname`.

### 4. Indexes, where column order mattered more than the column set

`state` has two useful values and `state IN ('open','reopened')` matches 83%
of the table, so it is a poor leading column. `exc_state_sev` leads on
`exception_id` (an equality) instead, which took the severity roll-up from
1.24 s to 0.15 s; the same index with `state` first was measurably worse.

Four single-column keys — `asset_id`, `vuln_id`, `state`, `exception_id` —
were leading prefixes of the new composites. They were not merely redundant:
a bare `exception_id` key had `GROUP BY severity` scanning 416,890 rows.
`pre_migrate()` drops them, so schema 13 adds five indexes and removes five.

| Index | Serves |
|---|---|
| `state_risk (state,risk_score,vuln_id,asset_id)` | default listing; the trailing two columns keep it covering when search adds the `IN` clauses — 9 s to 0.13 s |
| `state_sev_risk (state,severity,risk_score)` | severity-filtered listing — 1.10 s to 0.04 s |
| `exc_state_sev (exception_id,state,severity)` | severity roll-up on four screens |
| `vuln_state_exc (vuln_id,state,exception_id,asset_id)` | top-vulnerabilities panel — 7.6 s to under 0.2 s |
| `asset_state_exc (asset_id,state,exception_id,severity)` | per-team breakdown — 2.56 s to 0.22 s |
| `state_last_fixed (state,last_fixed)` | "fixed in the last 30 days" |

Re-running the migration is idempotent: `Install::run()` twice leaves the same
twelve indexes and dbDelta reports nothing further to do.
