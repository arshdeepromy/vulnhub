VulnHub's plugins never call into each other directly. A connector fires an action; the threat plugin, the rules engine, the widget cache and Jira all listen. To add behaviour, hook an existing extension point rather than editing another plugin. This page catalogues the ones worth knowing, plus the capability model and the CLI.

The golden rule. If you find yourself editing another plugin's file, stop and look for a filter or action first — there almost always is one. New tables, connectors, widgets, views and filters are all additive.

Actions — the events to listen on

vulnhub_sync_completeFired after any connector finishes, with ($connector_id, $status, $stats). The main integration seam — asset classification (pri 10), ownership mapping (pri 20), reachability rebuild, and the dashboard's cache bust (pri 99) and warm (pri 100) all hang off it.
vulnhub_import_completeA CSV import job finished successfully. Passes $type (tenable / cmdb), $job_id and the job counters, after merge, roll-ups, mapping and coverage have run.
vulnhub_coverage_recalculatedCoverage states were recomputed.
vulnhub_register_connectorsRegister a new connector object.
vulnhub_dash_render_view_<view>Render a contributed portal view.
vulnhub_render_portal_sectionRender a plugin-owned admin section.
vulnhub_render_admin_pageRender a wp-admin screen registered via vulnhub_admin_pages.
vulnhub_run_automations / vulnhub_verify_closuresTicket automation and closure-verification passes (Jira listens).
vulnhub_portal_header / vulnhub_portal_footer / vulnhub_portal_noticePrint a replacement header or footer (when the matching vulnhub_portal_has_custom_header / _footer filter returns true), or anything above the main region of every portal view.
vulnhub_portal_login_top / vulnhub_portal_login_bottomAdd markup to the sign-in screen.

vulnhub_import_complete fires once a CSV import job finishes successfully, after merge, roll-ups, ownership mapping and Coverage::recalculate() have run. It passes $type (tenable or cmdb), $job_id and the job's counters. Listeners that only want the signal should register with accepted_args 0, because the first argument is the import type, not a connector id.

The findings query — how the attack-path filters are built

vulnhub_findings_query is the extension point that lets a plugin add WHERE clauses, bound parameters and joins to the central findings query. It receives an array (where / params / need_asset / need_vuln) and the query args. This is exactly how the threat plugin teaches the findings list about route, delivery and poc:

add_filter( 'vulnhub_findings_query', function ( array $ext, array $args ): array {
    if ( ! empty( $args['my_flag'] ) ) {
        $ext['where'][] = 'f.risk_score >= 50';
    }
    return $ext;
}, 10, 2 );

Add the corresponding request key to the findings screen's arg builder so a URL parameter reaches your filter.

vulnhub_assets_query is the same idea for Repo::assets(), and it is how the hosting plugin teaches the assets list about hosting. It takes where and params — and no joins. That query is a flat select over the assets table with unaliased columns, and core's own clauses say things like id IN (…); join a second table carrying its own id and those clauses stop being unambiguous, so the query fails rather than returning the wrong rows. Contribute a self-contained subquery instead. Anything added here reaches the list, its infinite scroll and the CSV export together, which is the reason to put it in the query rather than in a screen.

Times: store UTC, display local

Every timestamp in the database is UTC. vh_now() is gmdate(), and MySQL's NOW() is UTC in these containers, so comparisons are UTC against UTC and need no conversion. Anything a person reads goes through vh_date(), vh_ago() or wp_date(), which render in the site's timezone.

A bare gmdate() or date() printed to screen is a bug. The site timezone had never been set here, so "local time" meant UTC and every screen — including the clock on every sync log line — read twelve hours behind for months. Settings → System now shows the timezone and says so when it is unset.

A date is not an instant. An end-of-life date, a plan deadline or a due date is a DATE column with no time in it, and converting it can move it a day: use vh_date_only(), which formats in UTC so 31 December cannot become 30 December. It also avoids printing a meaningless "00:00" after a date that never had a time.

Capabilities & roles

Capabilities live in \VulnHub\Core\Caps. Gate your features on these, not on WordPress's manage_options.

CapabilityGrants
Caps::VIEWRead the portal.
Caps::TRIAGETriage findings.
Caps::RAISE_TICKETRaise remediation tickets.
Caps::REQUEST_EXCEPTION / APPROVE_EXCEPTIONRequest / approve risk exceptions.
Caps::RUN_SYNCTrigger connector syncs.
Caps::VIEW_AUDITRead the audit trail.
Caps::MANAGEConfigure everything.

Four roles bundle these: vulnhub_viewer (VIEW), vulnhub_analyst (view, triage, raise, request, run sync, audit), vulnhub_approver (view, request & approve exceptions, audit) and vulnhub_admin (everything). WordPress administrators additionally hold every VulnHub capability. SSO-provisioned users default to viewer, with group→role mapping configurable.

Cron & CLI

WordPress cron is driven by a container running wp cron event run --due-now every 60 seconds. Connectors schedule themselves on custom intervals (5 min → weekly); the threat feeds refresh nightly. Heavy jobs are also WP-CLI commands so they can run without a request timeout:

wp vulnhub threat refresh     # re-pull NVD / KEV / EPSS and rebuild attack paths
wp vulnhub threat classify    # re-place every definition on a route
wp vulnhub threat status      # feed freshness and counts

Core also ships:

wp vulnhub classify-apps        # stamp the bundling app on findings from their scanner output
wp vulnhub classify-products    # [--dry-run] stamp product / kind / slug onto every vulnerability definition
wp vulnhub merge-duplicates     # merge split asset rows for one machine (the same sweep every import runs)
wp vulnhub stale-records        # list name-only CMDB records being held; --collect, --forget

Connector syncs and imports have no CLI command of their own: start them from the admin area, the MCP tool, or POST vulnhub/v1/connectors/<id>/sync. Watch any run under Admin → Sync activity.

Connectors: incremental and full resyncs

A connector that syncs incrementally from a watermark (Tenable, for live data) can also be asked to fetch everything the source holds. The base Connector class has three hooks for this, all no-ops by default:

supports_full_sync()Return true if "everything" is a different run from "what changed". This is what shows the Full resync button on the connector card.
request_full_sync()Record that the next fresh run should be full. It is a request, not a run: the sync is dispatched to cron and may first finish an interrupted run, so the intent has to outlive the web request. Tenable stores it in its own option (not the connector settings array, which a running sync saves back whole and would overwrite) and clears it only when a full run completes.
full_sync_note()One line for the connector card — last full resync, when the next is due, or a pending request.

POST vulnhub/v1/connectors/<id>/sync with full=true calls request_full_sync() and queues the run in the background for any connector whose async_sync() is true; the MCP vulnhub_sync_connector tool routes the same way. Only a connector that syncs inline receives full directly in do_sync( $args ). Tenable decides full-or-incremental once when a fresh run starts (first sync, a pending request, or Full resync every N days elapsed) and records it in the run's state.json, so a resumed run stays whatever it started as. See Where the data comes from for what each kind of run fetches.

Adding a whole new data source? Extend the abstract Connector, register it on vulnhub_register_connectors, write assets/findings through Core's Repo (so fingerprinting, dedup, lifecycle and roll-ups come for free), store secrets through the encrypted settings store, and let vulnhub_sync_complete do the rest.
