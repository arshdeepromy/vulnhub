VulnHub does not scan anything itself. It is a correlation layer: it pulls from the systems you already run — your scanner, your device manager, your CMDB, your cloud — reconciles them into one asset register, and enriches everything with public threat intelligence. This page explains each source, what it contributes, and how often it runs.

Tenable — the spine

Tenable is the primary source. It brings in the asset inventory and every vulnerability finding through Tenable's asynchronous export API (request → poll → download in chunks, so a huge export never has to fit in memory). By default it imports Critical→Low findings (informational findings are left out — they would more than double the row count). It keys assets on their Tenable UUID and findings on the scanner plugin id. Tenable's own FIXED state is what closes a finding — VulnHub never guesses "fixed" from absence.

A companion verifier runs hourly: when a remediation ticket closes, it waits a settling period (default 24h) then re-runs a narrowed scan export to prove the finding is gone. Still-detected findings are flipped back to reopened.

Intune & Entra ID — devices and people

Microsoft Graph provides two things: managed devices (compliance state, enrolment, "is it managed", last sync) and the Entra people directory (names, managers, departments, office). The connector deliberately does not set an owner directly — it records each device's primary user, and Core's ownership-mapping engine later resolves that to a person, a team (from department) and a location (from office). Owners resolved this way are high-confidence.

CMDB — the authority on ownership and lifecycle

The CMDB (ServiceNow table API, a Confluence page, or a CSV) is the authority for what a machine is for: its criticality, environment, business service, support group and lifecycle status. It has guard rails so it can never do harm — it will not overwrite another connector's asset type, and if it claims a machine is decommissioned but Tenable scanned it recently, the conflicting lifecycle change is recorded rather than applied (so a stale CMDB record can't archive live findings).

AWS — cloud reachability

The AWS connector is unusual: it does not create assets. It reads security groups, route tables and load balancers (and Amazon Inspector's network-reachability findings) to decide which EC2 instances are genuinely reachable from the internet — direct (a security group open to 0.0.0.0/0 on a public IP with an internet gateway route) or elb (behind an internet-facing load balancer). It then feeds that verdict into the reachability engine for instances Tenable already inventoried.

Threat context — the public feeds

Nightly, the threat plugin pulls three free, unauthenticated feeds — NVD (for CVSS vectors), CISA KEV (known-exploited), and FIRST EPSS (exploit probability) — and rebuilds the attack-path and exploitability data. None of your estate ever leaves the box to fetch these. See Routes, delivery & reachability and Severity, KEV, EPSS & VPR.

How a sync runs

Every connector shares one framework. A run:

  • takes a 30-minute lock (no two runs of the same connector overlap);
  • opens a row in the sync ledger (sync_runs) recording mode, counts (processed / created / updated / skipped / failed), a message and a full log;
  • upserts assets, vulnerabilities and findings — findings de-duplicated by a fingerprint, and matched on (asset, vulnerability) first so port/protocol drift enriches a row instead of duplicating it;
  • on success fires vulnhub_sync_complete, which triggers asset classification, ownership mapping, reachability rebuild, and a targeted widget-cache bust.

You can watch every run under Admin → Sync activity, including its log. Cron is driven by a dedicated container running WordPress's scheduler every 60 seconds, so scheduled work happens even when nobody has the site open.

Imports are tracked separately. CSV imports are large, resumable jobs with their own ledger (import_jobs) and their own progress UI under Admin → Imports — they never write to the connector ledger. When an import finishes, it runs the same housekeeping a live sync would (lifecycle sweep, de-duplication, roll-ups, ownership mapping, coverage).

How the same machine from three systems becomes one asset

An asset can be discovered by Tenable, managed by Intune, recorded in the CMDB and seen by Defender — VulnHub merges them into a single row by matching on the strongest identifier available (Tenable UUID, Intune id, Azure AD device id, serial number, then hostname). Each contributing system is remembered in the asset's sources_json, and the "discovered by" and coverage widgets are built from exactly which systems have and haven't seen each machine. This is why coverage gaps are a first-class concept: a server the CMDB knows about but Tenable has never scanned is precisely the blind spot the dashboard is built to surface.
