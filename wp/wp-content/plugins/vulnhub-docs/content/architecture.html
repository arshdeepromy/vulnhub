VulnHub is a set of sibling WordPress plugins built around a core. Each plugin owns one concern and talks to the others through WordPress filters and actions — there is no shared God-object beyond vulnhub() (the Core singleton). This page is the map a new developer needs before opening any single file.

The runtime it lives in

The application runs as a Docker Compose stack (~/vulnhub): a wordpress:php8.3-apache container serving the app on port 8093, MariaDB 11, a Redis object cache, a WP-CLI container, a cron loop container that runs wp cron event run --due-now every 60 seconds, and MailHog for captured mail. The portal answers both on localhost:8093 and behind a Cloudflare tunnel at the public hostname — which is why widget HTML is cached per host (absolute links get baked in).

The eighteen plugins

Core boots on plugins_loaded at priority 5 and then fires vulnhub_register_connectors, which is where the connector plugins (Tenable, Intune, CMDB, Jira, AWS, Auth) register. Most other plugins boot on plugins_loaded at priority 20. Plugins load alphabetically, so vulnhub-alerts, vulnhub-auth and vulnhub-dashboard load before Core: none of them may test for vulnhub() at file scope — they check on plugins_loaded instead.

The spine

vulnhub-coreThe estate and the shared library. Owns the assets, vulns (scanner definitions), findings, exceptions, teams, tickets and more tables; the Repo data layer; capabilities and roles (Caps); product classification; the finding lifecycle; the scheduler; and the vulnhub() singleton every other plugin depends on.
vulnhub-dashboardThe portal itself: the app shell, the view/nav/page framework, the whole dashboard widget system (registry, layout, caching, CSV export), and the admin area. If you are building UI, you are mostly here.
vulnhub-threatCVE intelligence and attack-path classification. Pulls NVD, CISA KEV and FIRST EPSS; builds the cve_intel, vuln_paths, asset_exposure and asset_ports tables; draws the "How an attacker gets in" widget.
vulnhub-rulesThe asset-classification engine — ordered rules with conditions that set an asset's environment, criticality, type, business service and priority weight.

Connectors (data in)

vulnhub-tenableThe primary scanner connector — pulls assets and vulnerability findings from Tenable.
vulnhub-intuneMicrosoft Intune & Entra ID — device inventory, management and identity signals.
vulnhub-cmdbCMDB reconciliation — authoritative asset ownership, location and lifecycle.
vulnhub-awsAWS accounts and cloud exposure signal.
vulnhub-importBatched, resumable CSV import for very large CMDB and Tenable exports. Microsoft Defender device data also arrives through this CSV path.
vulnhub-departmentsEnriches existing people with their Entra department; adds the Department filter, the Vulnerabilities by department widget, a hidden departments view and an admin section. Never creates users.
vulnhub-hostingClassifies servers as cloud (AWS / Azure / GCP) or on-prem; adds the hosting findings filter and the Servers by hosting environment widget.

Workflow & output

vulnhub-jiraRaises and syncs remediation tickets in Jira Cloud, with an automation/routing engine and a reopener for still-detected issues.
vulnhub-alertsWatches advisory / zero-day feeds (EUVD, MSRC, CISA, GitHub, Red Hat, Ubuntu) and reports which advisories can actually reach your estate. Adds its own portal view and a nav badge.
vulnhub-backupBatched, resumable backup & restore, with optional scheduled push to S3.
vulnhub-mcpA Model Context Protocol server: lets an AI agent read and (audited) write the estate over JSON-RPC, authenticated by bearer tokens.
vulnhub-authIdentity: portal sign-in, SSO (Okta / Entra / generic OIDC), MFA, LDAP/AD, and the people directory.
vulnhub-elementorExposes the live dashboard widgets as Elementor widgets and lets Elementor Pro build the portal header/footer.
vulnhub-docsThis handbook: a contributed docs view and a Documentation admin section.

How a request flows

  1. A visitor hits a portal page (say /vulnerabilities). Each portal page is a normal WP page whose only content is the shortcode [vulnhub_app view="…"].
  2. On template_redirect, guard_portal() sends a logged-out visitor to /sign-in/, and redirect_signed_in() sends a signed-in visitor who lands on sign-in to the dashboard.
  3. vulnhub-dashboard swaps the theme template for its own shell (templates/app.php) via template_include, renders the icon rail (unless a custom header is assigned), and calls render_view($view) inside the main region.
  4. render_view() draws the sign-in view first if that is the request; otherwise it checks access (gate() → needs Caps::VIEW), then dispatches: a plugin-contributed view is drawn by its vulnhub_dash_render_view_<view> action; the built-in views fall through a switch.
  5. The view asks Core's Repo for numbers. Dashboard widgets render through a serve-stale cache keyed by a per-widget epoch, so most requests never touch the database.

How data flows in

  1. A connector (Tenable, Intune, CMDB, AWS) runs on its cron schedule, or an operator uploads a CSV through vulnhub-import.
  2. Rows are upserted into assets / vulns / findings; each finding is de-duplicated by a fingerprint. A finding changes state because the scanner reports it changed (Tenable sends FIXED / REOPENED), and a finding re-sent unchanged only has its last-seen time moved.
  3. On vulnhub_sync_complete, the classification chain runs: the rules engine classifies assets (priority 10), then Core's ownership mapping resolves owners (priority 20), then the threat plugin rebuilds exposure and attack paths.
  4. The same hook busts the widget cache for exactly the sources that connector moved, so the dashboard reflects the new data without rebuilding everything.
  5. A CSV import does not fire vulnhub_sync_complete: the import runner merges duplicates, rolls up, runs ownership mapping and recalculates coverage itself, and the widget cache is busted through vulnhub_coverage_recalculated.

The golden rule of coupling here: plugins never call into each other directly. A connector fires vulnhub_sync_complete; the threat plugin, the rules engine, the widget cache and Jira all listen. To add behaviour, hook an existing action rather than editing another plugin. The hooks worth knowing are catalogued in Filters & extension points.
