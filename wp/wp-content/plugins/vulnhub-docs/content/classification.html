Every open finding in VulnHub is placed on a single attack path: the shortest way somebody could actually reach and use it. This is what turns a list of 200,000 findings into a picture you can act on — most of that list can only be used by someone who is already inside, and the handful that a stranger can reach from the internet is the part that should keep you up at night. This page explains exactly how that placement is decided, so you can trust the numbers and, as a developer, reproduce them.

Where this is computed. Route, delivery and reachability all live in the vulnhub-threat plugin. The nightly refresh pulls CVE intelligence (NVD, CISA KEV, FIRST EPSS), then VulnHub_Threat_Classify::rebuild_all() rebuilds the vulnhub_vuln_paths table that every attack-path number reads from.

The three routes (and the honest fourth)

A finding is sorted into the order an intrusion actually runs:

edgeReached straight from the internet. A stranger opens a socket to something you publish — no account, no user, no click. This is the lane where the number should be zero.
userDelivered to one of your people. A stranger sends something a person opens — an email attachment, a link, a download. It is split three ways (email / website / download) because the countermeasures belong to three different teams.
insideOnly usable once somebody is already in. Privilege escalation and lateral movement. Not a third door — it is what waits on the other side of the first two.
unknownNo route could be inferred. The CVE published no CVSS v3 vector, so there is nothing to reason from. These are counted and shown, never hidden or guessed onto a lane.

How a CVE is assigned a route

The route comes entirely from the CVE's CVSS v3 vector — the attack vector, privileges required and user interaction fields that NVD publishes. No human judgement is added. The rule, evaluated in this exact order:

route = CASE
  WHEN attack_vector = ''                                         THEN 'unknown'
  WHEN user_interaction IN ('REQUIRED','PASSIVE','ACTIVE')        THEN 'user'
  WHEN attack_vector = 'NETWORK' AND privileges_required = 'NONE' THEN 'edge'
  ELSE 'inside'
END

The order matters:

  • User interaction wins over everything. If a bug needs someone to open a file, it is delivered to a person regardless of its network vector.
  • "Network + no privileges" is the only unauthenticated-stranger combination — that is edge.
  • Everything else needs a foothold first — adjacent-network, local or physical vectors, or anything that requires some privilege — so it falls to inside.

CVSS v2 cannot answer this. Version 2 has no user-interaction or privileges field, so a v2-only CVE keeps its score but has a blank vector and is routed unknown. Vectors are read from NVD preferring v3.1 → v3.0 → v4.0. Also note "adjacent network" is normalised to ADJACENT_NETWORK, which is not NETWORK — so adjacent-network CVEs are inside, not edge.

From a CVE to a scanner definition

The dashboard does not count CVEs — it counts findings, and each finding points at a scanner definition (one Tenable plugin, such as "RHEL 9 : kernel (RHSA-…)"). A single definition can name thirty CVEs. VulnHub rolls the CVEs up to the definition and keeps its most reachable route, because patching is per-package: a kernel advisory bundling thirty CVEs is exactly as exposed as its worst one. Two roll-ups are stored per definition:

routeThe most reachable route among all the definition's CVEs.
poc_routeThe most reachable route considering only CVEs that have a working exploit (has_poc = 1). This is the column the "How an attacker gets in" widget filters on, because it only counts exploitable findings.

Delivery channels: email, website, download

Within the user route, each finding is further tagged with how it reaches the person. This is a refinement of a lane the CVSS vector already decided — a wrong guess moves a finding between email/website/download, never between routes.

mailArrives through an email client (Outlook, Thunderbird, SMTP/IMAP, S/MIME, a calendar invite, message preview).
webArrives by visiting a page or link (a browser, JavaScript engine, HTML/CSS, XSS). This is the catch-all: any user-route finding that is not clearly mail or file counts as web.
fileArrives as a downloaded, opened document or archive (a crafted file, Office document, PDF, zip, font, installer, macro).

The channel is decided by keyword-matching the CVE's English description, tested in the fixed order mail → file → web (mail clients also render web content and open attachments, so mail must be tested first). If nothing matches, a NETWORK vector falls back to web (a network click is a link) and anything else to file (a local thing handed over and opened).

Reachability: is this asset actually on the internet?

The edge lane is only as honest as the answer to "can the internet really reach this machine?" — and that has three answers, not two. VulnHub records a verdict and, just as importantly, the basis for it:

Reachable (confirmed)Something was actually observed — a perimeter tag, a public routable IP address, a cloud network that answered, or a web/mail service listening. Basis: evidence.
Ruled outWe have listening-port data for this machine and nothing publishable was listening. Basis: ruled_out.
Never lookedNo listening-port scan has ever run against it. It is neither confirmed reachable nor confirmed safe — a coverage gap, not an all-clear. Basis: unknown.

Why "never looked" is printed at all. Before the listening-port inventory existed, exposure was decided by asset type — hundreds of machines were called "internet-facing" for being labelled server, and the widget reported thousands of findings as reachable with no account and no click. The evidence supported a couple of dozen. Printing "we have not looked at N of them" is the difference between an honest floor and a false all-clear, which is why the edge lane is described as "a floor, not a total" whenever unscanned servers remain.

The default rule is evidence-first (observed)

Under the default observed exposure rule, a machine is judged reachable only on observed evidence, decided in this precedence:

  1. A perimeter tag on the asset (internet-facing, dmz, public-facing, edge, perimeter).
  2. A cloud provider that reports the instance as reachable (only available when a cloud connector is configured — the one source that sees the network, not the host).
  3. A public routable IP address. Private ranges (RFC1918), carrier-grade NAT / Tailscale (100.64.0.0/10) and SD-WAN/benchmarking overlays (198.18.0.0/15) are explicitly not counted as internet-reachable.
  4. A publishable service listening — a web or mail port answering.
  5. Otherwise, if the machine was never port-scanned → "never looked".
  6. Otherwise → "ruled out".

Being typed a server earns nothing under observed. Verdicts a person set by hand are left untouched by a rule pass. Administrators can switch the rule (to all, cloud_only, tagged or the legacy servers_and_cloud) under Admin → Rules, but observed is the honest default.

The listening-port evidence

The "what is listening" inventory is built from two Tenable Netstat Portscanner plugins (34220 over WMI, 14272 over SSH) — informational findings that are otherwise suppressed, so the data was invisible until this plugin surfaced it. Of the ports another machine could connect to, only web and mail listeners count as evidence of a plausible perimeter host. This inventory answers "is something listening"; it can never answer "can the internet route to it" — no scanner supplies firewall or routing rules, and VulnHub never pretends otherwise.

What happens to edge findings on unreachable machines

An edge-route finding on a machine the internet cannot reach is not thrown away — it is moved to the inside lane, because that is where it can actually be used (by someone who already has a foothold). This is why the inside lane's total is larger than "purely local" bugs alone, and the widget labels this the "borrowed" portion.

Putting it together

So, reading the attack-path widget from left to right: a finding starts as one or more CVEs, each routed purely from its CVSS vector; the CVEs roll up to a scanner definition keeping the worst exploitable route; the definition's findings are then split by whether the machine is genuinely reachable (edge) or not (moved inside), and user-route findings are fanned out across email/website/download. Every number is a link into the exact findings it counted — see The dashboard, widget by widget for how to drill in, and Severity, KEV, EPSS & VPR for what "exploitable" is built from.
