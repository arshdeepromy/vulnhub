The portal is a thin routing layer over WordPress pages. Every screen is a normal published page whose only content is a shortcode; the dashboard plugin swaps in its own template, renders the chrome, and dispatches to a per-view renderer. This page shows how to add a view, a nav link or an admin section — the three ways to put something new in front of a user. All references are in vulnhub-dashboard.

This docs section is itself a worked example: it is a contributed view (docs) with a nav link and an admin section, built entirely on the extension points below — no core files were edited.

Views

The registry is vulnhub_dash_views() in vulnhub-dashboard.php. Each entry is keyed by a view name and carries title, slug, menu, an SVG icon path, and optional hidden. On activation the dashboard creates one published page per view whose content is [vulnhub_app view="<view>"], and records view → page id in the option vulnhub_dash_pages (the single source the nav reads to build links).

A view is stronger than a mere nav link: it is a page the portal owns and renders itself. Add one with the vulnhub_dash_views filter, but note the doc contract — because the registry is read long after activation, a contributed view must also create its own page and answer its render action:

// 1) Register the view.
add_filter( 'vulnhub_dash_views', function ( array $views ): array {
    $views['runbook'] = array(
        'title' => __( 'Runbook', 'vulnhub' ),
        'slug'  => 'runbook',
        'menu'  => __( 'Runbook', 'vulnhub' ),
        'icon'  => 'M4 4h16v16H4z',   // an SVG path
        // 'hidden' => true,          // routable, but not in the primary nav
    );
    return $views;
} );

// 2) Render it (echo the body; the shell chrome is already drawn).
add_action( 'vulnhub_dash_render_view_runbook', function (): void {
    echo '<h1>Runbook</h1>…';
} );

// 3) Ensure its page exists and is mapped in vulnhub_dash_pages
//    (create it on your plugin's activation, like the docs plugin does).

How rendering is dispatched

VulnHub_Dash_App::render_view($view) runs after access is checked. It looks for vulnhub_dash_render_view_<view> first — so a contributed view is drawn by its own action and can never be swallowed by the built-in switch. The built-in views (vulnerabilities, assets, tickets, …) fall through that switch. The [vulnhub_app] shortcode is the fallback path for block/theme contexts; the primary path is a template_include swap to templates/app.php, which renders the nav and then calls render_view() inside <main>.

Navigation

render_nav() draws the portal chrome. It still outputs <header class="vh-topbar">, but app-redesign.css turns it into a fixed 64px icon rail down the left edge: labels are visually hidden and appear when the rail is hovered or focused (it widens to 224px as an overlay, so the page never reflows), and below 768px it becomes a sticky bar across the top. The rail lists every view that is not hidden and has a mapped page, then any vulnhub_portal_nav_extra links. Its foot holds the light/dark toggle, the Administration link (only with Caps::MANAGE) and the account menu (Security & MFA, Sign out). body_class() adds vh-app-body on every portal page, vh-chrome-rail when the portal draws its own rail, and vh-login-body on sign-in.

For a link that is not a full view — an Elementor page, an external tool — use the vulnhub_portal_nav_extra filter:

add_filter( 'vulnhub_portal_nav_extra', function ( array $links ): array {
    $links[] = array(
        'label'  => 'Tenable',
        'url'    => 'https://cloud.tenable.com',
        'icon'   => 'M4 4h16v16H4z', // optional
        'active' => false,           // optional
    );
    return $links;
} );

An entry with no url or no label is dropped, icon defaults to a square, and extra links appear in the rail after the built-in views. The Administration link is rendered separately and only for users with the manage capability; the admin view is hidden so it never appears in the main loop.

Page layout

The body reserves the 64px rail with padding-left, and .vh-main and the footer centre themselves in the remaining width up to --vh-content-max (1440px). On a wide or zoomed-out window the spare space is split evenly on both sides of the column rather than piling up on the right. Below 768px the rail becomes the top bar and the column uses the full width. The sign-in view is full-bleed and reserves nothing.

Replacing the chrome

If vulnhub_portal_has_custom_header returns true (vulnhub-elementor does this when a Theme Builder header is assigned), templates/app.php fires vulnhub_portal_header instead of render_nav(), and vh-chrome-rail is not added, so no rail space is reserved. vulnhub_portal_has_custom_footer / vulnhub_portal_footer do the same for the footer. vulnhub_portal_notice fires between the chrome and <main>. The sign-in view draws neither header nor footer.

Assets & theme

VulnHub_Dash_App::assets() registers its handles everywhere but enqueues them only on portal pages: app.css, app-redesign.css, app.js (depends on wp-api-fetch; localised as VulnHubApp with nonce, restRoot and i18n) and vh-motion.js. Each version string is the plugin version plus the file's mtime, so a CDN treats an edited file as a new object. Sign-in additionally loads login.css, login.js, attack-surface-bg.js and web fonts, and dequeues Elementor's front-end bundles. The UI is dark by default; html[data-theme="light"] swaps the token set, and a pre-paint script restores the choice from localStorage['vh-theme']. A contributed view enqueues its own assets (the docs plugin does so on its page) and should style with --vh-* tokens so both themes work.

Guarding & access

Two layers protect the portal:

  • guard_portal() (on template_redirect) sends a logged-out visitor on a portal page to the sign-in screen.
  • gate() (inside render_view()) requires Caps::VIEW for every non-login view. A logged-in user without a VulnHub role gets an inline "not granted a role" notice rather than a redirect loop.

The sign-in view is handled before gate(), so it is always reachable. The admin view additionally checks each section's own capability and hides sections you cannot open. The WordPress admin bar is hidden on every portal page, for everyone. A portal-only user is a runtime concept, not a role: logged in, holds Caps::VIEW, but lacks manage_options. Any wp-admin screen redirects such a user back to the portal (admin-post.php and admin-ajax.php are exempt, so portal forms still save), and signing in sends them straight to the dashboard. Roles and capabilities are covered in Filters & extension points and defined in vulnhub-core's Caps class.

Portal links stay in the portal: the account menu's Security & MFA opens the Your security admin section (registered by vulnhub-auth, capability vulnhub_view), and the Except button on a findings row opens the request form inside the Exception register. Both used to point at wp-admin, which bounced portal-only accounts back to the dashboard.

Admin sections

The admin area's section list is VulnHub_Dash_Portal::sections(), filterable via vulnhub_portal_sections. A section has a label, a required cap, a group (data / integrations / platform), an order, and a summary. If it names a screen, core's render_screen() draws it; otherwise the portal tries vulnhub-dashboard/admin-views/<section>.php (that directory does not currently exist), and then fires do_action('vulnhub_render_portal_section', $section) — the seam for a plugin-owned section. Imports and Rules, for example, are core section entries with no screen, answered by vulnhub-import and vulnhub-rules:

add_filter( 'vulnhub_portal_sections', function ( array $s ): array {
    $s['runbook'] = array(
        'label'   => __( 'Runbook', 'vulnhub' ),
        'cap'     => \VulnHub\Core\Caps::VIEW,
        'group'   => 'platform',
        'order'   => 80,
        'summary' => __( 'Operational runbook.', 'vulnhub' ),
    );
    return $s;
} );

add_action( 'vulnhub_render_portal_section', function ( string $section ): void {
    if ( 'runbook' !== $section ) { return; }
    echo '…section body…';
} );

Gotchas. group must be exactly data, integrations or platform — any other value registers a section that never appears in the side nav. The render action fires for every section without a screen, so always check $section first. An unknown ?section= falls back to overview.

Integration plugins that register wp-admin screens via vulnhub_admin_pages are mirrored into portal sections automatically as screen-<slug> — they register once and appear in both places with no extra code, marked with a WP badge in the side nav. Tenable, Intune, CMDB, Jira, Automation and Backup land in the Integrations group; Authentication and End of life (slugs containing auth or lifecycle) land in Platform. Core screens the portal already covers natively (findings, assets, tickets, exceptions, integrations, sync, audit, settings, ownership) are not mirrored.

The admin shell

The section list defaults to overview (which needs Caps::MANAGE). Above the body sits a context bar with the breadcrumb, a MOCK DATA badge when sample data is on, and connector health ("N connectors failing / idle"). The side nav has a Filter sections… box and a red dot on Integrations while a connector's last run failed. A save handler that redirects with vh_type=success&vh_msg=… shows a "Saved" chip. The footer shows when Tenable, CMDB, Intune and Jira last ran, plus the core and schema versions. A form posted from the portal carries vh_from_portal (or a portal referer), and vh_admin_url() redirects are then rewritten to the matching portal section instead of wp-admin.

Every vulnhub-dashboard/v1 route requires a logged-in user with Caps::VIEW.

Gotchas

  • view_for_post() matches the page content literally on view="<name>" with double quotes — a page written with single quotes is served as the dashboard.
  • The sign-in screen has its own filters and actions: vulnhub_portal_login_wordmark, vulnhub_portal_login_host, vulnhub_portal_request_access_url, vulnhub_portal_privacy_url, vulnhub_portal_terms_url, vulnhub_portal_status_url, and the actions vulnhub_portal_login_top / vulnhub_portal_login_bottom.
