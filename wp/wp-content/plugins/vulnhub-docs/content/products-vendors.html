Findings are easiest to act on when grouped by the software that carries them: patch one product across the fleet and many findings close at once. VulnHub classifies every vulnerability into a product and a kind, and the Products and Vendors screens (and the Exposure by product dashboard widget) roll findings up that way.

How a finding is mapped to a product

Tenable ships no clean product identifier on this feed, so VulnHub derives one from the plugin title (with the family as a coarse filter). It stamps four fields on each vulnerability definition:

component_classBroad bucket: os_linux, os_windows or third_party.
product_kindos_package (a Linux package), os_update (a Windows/Microsoft update), library (a component other software bundles), or application (an app in its own right).
productThe human name — "Google Chrome", "Apache Log4j", "Microsoft .NET", or a Linux group like "Linux: RHEL".
product_slugThe URL-safe key used for grouping and filtering (and, incidentally, for the product's icon).

Library vs application matters: a name is treated as a library if it is a known component (libcurl, openssl, sqlite, log4j, glibc, openssh, …) or begins with lib; otherwise it is an application.

Bundled libraries — attributed to the app that ships them

A vulnerable copy of, say, libcurl is rarely something you patch directly — it lives inside an application that shipped it. When VulnHub can read the install path from the scanner output, it attributes the library finding to the application that carries it, and the product roll-up regroups it there. That is why the widget can say "Ships a vulnerable libcurl inside the app — update the app, or check the vendor for a fixed release", and why the product with the most exposure is often an app, not the raw library.

The Exposure by product widget

Each row is a product, ordered by the number of assets affected (the machines you'd have to touch), with total findings beside it and a proportional bar against the top row. A kind badge marks it as library / app / OS. The list counts open, non-excepted, non-info findings in the reporting scope. Because the top rows move the number fastest, this is the widget to work top-down.

Performance note. The product roll-up is served from a summary table that the warm job rebuilds after each bust, with a live aggregate (cached for six hours, keyed by the widget epoch) as the fallback whenever that table is not current. If a new deployment shows "No products classified yet", run wp vulnhub classify-products once.

The Products screen

Opened from "View all" on the widget (it is not in the navigation). It lists every product and bundling application with no top-N cap, with a platform filter (All, Workstations, Servers, Windows, Linux), a name search, a By vendor link and an export. A product name opens the Vulnerabilities list filtered to exactly that row (product=…&pkind=…&life=reportable&state=open_any&sev_not=info&excepted=exclude). Both product and pkind travel, because the same software can appear twice — once as the operating-system package and once as the application or library — and a slug on its own would open both halves. The two cuts the counts are made with (informational detections and accepted risk) travel too, and the banner on the list says so. The same roll-up, over whatever filters you have applied, is also the By product tab on the Vulnerabilities screen.

Vendors

The Vendors screen (primary navigation) lists every vendor behind the estate: hardware makers from each asset's manufacturer, and software owners from each finding's product. A card shows its kind, an exposure band (open critical/high plus coverage gaps), and clickable counts — assets, products, findings, critical, uncovered, archived — each of which opens a drill-down with search, a severity filter, paging and CSV export. Links go to the vendor's security advisories and a public risk rating. Filter by All, Hardware, Software or Uncovered (assets that Tenable has not scanned, Defender has not onboarded and the CMDB does not record — blind spots that are still real hardware).

Icons

Products show a real brand logo when one is bundled (stored locally under the dashboard plugin's assets/products/<slug>.svg or .png), fall back to a clean single-colour motif for a set of well-known components (class-vh-product-icons.php, extensible with the vulnhub_product_icons filter), and otherwise show a brand-coloured monogram chip. Vendor cards use assets/vendors/<slug>.png the same way. Adding a missing logo is just dropping a correctly-named file into the right folder.
