A dashboard widget is three things: data, a way to draw it, and a way to export it. The framework in class-vh-dash-widgets.php gives you the frame, the drag handle, the export menu, per-user layout and a serve-stale cache for free. You provide a registry entry and one or two callbacks.

The registry entry

Widgets are registered through the vulnhub_dashboard_widgets filter. Each entry is keyed by a unique id:

add_filter( 'vulnhub_dashboard_widgets', function ( array $w ): array {
    $w['my_widget'] = array(
        'label'   => __( 'My widget', 'vulnhub' ),   // header title
        'summary' => __( 'One line of what it shows.', 'vulnhub' ),
        'group'   => 'exposure',   // a groups() key: exposure|lifecycle|coverage|endpoint|ownership|remediation
        'width'   => 6,            // default span; must be one of 3,4,6,8,12
        'depends' => array( 'findings' ),  // data sources it reads (drives cache invalidation)
        'render'  => 'my_render_cb',       // REQUIRED: echoes the body
        'data'    => 'my_data_cb',         // optional: enables CSV / Copy as TSV
    );
    return $w;
} );
renderRequired. A callable that echoes the widget body. If the output contains an <svg>, the export menu automatically offers PNG/SVG.
dataOptional. Returns ['headers'=>[…], 'rows'=>[…]] — the same numbers the chart drew, so the picture and the spreadsheet can never disagree. Its presence enables CSV and "Copy as TSV".
dependsOptional. The data sources this widget reads (findings, assets, coverage, defender, tickets, threat). Drives which syncs bust its cache. Declaring nothing means it depends on everything — safe, but it will be rebuilt on every sync.

Surfacing it by default

Registering a widget adds it to the picker. To put it on new boards by default, append to vulnhub_dashboard_default_layout:

add_filter( 'vulnhub_dashboard_default_layout', function ( array $layout ): array {
    $layout[] = array( 'id' => 'my_widget', 'width' => 6 );
    return $layout;
} );

Existing users pick it up automatically: the framework tracks which widgets a user has seen (distinct from removed), appends a newly shipped widget once, and leaves it off if they later remove it. This is exactly how the attack-path widget inserts itself right after the headline.

Widths & groups

The grid is 12 columns. Legal widths are 3, 4, 6, 8, 12; anything else is snapped back to the widget's default. The picker groups are Exposure, End of life, Tenable coverage, Defender coverage, Ownership and Remediation — the coverage groups are deliberately separate so their non-comparable percentages aren't mistaken for one number.

What the framework does for you

  • The frame & header — title, summary, a keyboard-operable drag handle, and the export menu (PNG/SVG when there's an SVG, CSV/TSV when there's a data callback).
  • Per-user layout — arrangement is saved to user meta and sanitised on save (unknown ids dropped, widths snapped), whether saved by drag (REST) or the JS-off Customise form (admin-post). A user can never store a widget they can't see.
  • CSV export — served from a nonced admin-post.php endpoint, gated by Caps::VIEW, straight from your data callback.

The cache — read this before you wonder why a change didn't show

Rendered widget HTML is cached in a transient keyed vh_w_<md5(id|locale|home_url)> (the host is in the key because widget HTML carries absolute links and this app answers on two hostnames). There are two horizons: 15-minute freshness and 6-hour serve-stale. On render the board serves the cached copy immediately and, if stale, queues a background re-render — so a sync never makes a visitor wait.

Invalidation is by epoch stamp travelling inside the cache entry, not in the key — so a bust marks markup stale rather than hiding it. Each widget's stamp is composed from its depends sources plus a global floor. When a connector finishes, bust_for_connector() maps it to the sources it moved (e.g. tenable → findings, assets, coverage; jira → tickets; threat → threat, findings) and ticks only those — so only the affected widgets rebuild. A whole-board warm job re-renders the default layout plus everyone's saved widgets on cron.

Consequence for development and content edits: editing a widget's PHP does not change what visitors see until its cache entry rolls or is busted. During development, flush the object cache (wp cache flush) after a change. In production, a connector sync busts the right widgets automatically.

A note on live vs cached data

Most widgets run their SQL live on each (uncached) render, so freshness tracks the last sync. Two add their own caching — Exposure by product (a materialised summary table plus a 6-hour transient) and Patch availability (a per-request memo). The trend widget is special: it reads a pre-aggregated nightly snapshot table, not live findings, because it is plotting history.
