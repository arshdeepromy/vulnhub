A dashboard widget is three things: data, a way to draw it, and a way to export it. The framework in class-vh-dash-widgets.php gives you the frame, the drag handle, the export menu, per-user layout and a serve-stale cache for free. You provide a registry entry and one or two callbacks.

The registry entry

Widgets are registered through the vulnhub_dashboard_widgets filter. Each entry is keyed by a unique id:

add_filter( 'vulnhub_dashboard_widgets', function ( array $w ): array {
    $w['my_widget'] = array(
        'label'   => __( 'My widget', 'vulnhub' ),   // header title
        'summary' => __( 'One line of what it shows.', 'vulnhub' ),
        'group'   => 'exposure',   // a groups() key: exposure|lifecycle|coverage|endpoint|ownership|remediation
        'width'   => 6,            // default span; must be one of 3,4,6,8,12
        'depends' => array( 'findings' ),  // data sources it reads (drives cache invalidation)
        'render'  => 'my_render_cb',       // REQUIRED: echoes the body
        'data'    => 'my_data_cb',         // optional: enables CSV / Copy as TSV
    );
    return $w;
} );
renderRequired. A callable that echoes the widget body. If the output contains an <svg>, the export menu automatically offers PNG/SVG.
dataOptional. Returns ['headers'=>[…], 'rows'=>[…]] — the same numbers the chart drew, so the picture and the spreadsheet can never disagree. Its presence enables CSV and "Copy as TSV".
dependsOptional. The data sources this widget reads (findings, assets, coverage, defender, tickets, threat). Drives which syncs bust its cache. Declaring nothing means it depends on everything — safe, but it will be rebuilt on every sync.

Surfacing it by default

Registering a widget adds it to the picker. To put it on new boards by default, append to vulnhub_dashboard_default_layout:

add_filter( 'vulnhub_dashboard_default_layout', function ( array $layout ): array {
    $layout[] = array( 'id' => 'my_widget', 'width' => 6 );
    return $layout;
} );

Only widgets placed in the default layout reach existing boards. The framework tracks which widgets a user has seen (distinct from removed): the next time someone who has saved a layout opens the dashboard, any default-layout widget they have never seen is appended at the end of their board at its default width and saved; if they remove it, it stays removed. Your filter's position (the attack-path widget splices itself in right after headline) only applies to users who have never saved a layout.

Register early. all() memoises the registry for the rest of the request, so hook vulnhub_dashboard_widgets on plugins_loaded or init, not later.

Widths & groups

The grid is 12 columns. Legal widths are 3, 4, 6, 8, 12; anything else is snapped back to the widget's default. The picker groups are Exposure, End of life, Tenable coverage, Defender coverage, Ownership and Remediation — the coverage groups are deliberately separate so their non-comparable percentages aren't mistaken for one number.

What the framework does for you

  • The frame & header — markup section.vh-w.vh-w--{width}[data-vh-widget][data-vh-width] containing header.vh-w__head and div.vh-w__body; title, summary, a drag handle that also responds to arrow keys, and the export menu. PNG/SVG appear only when your rendered HTML contains <svg; CSV appears when there's a data callback. vh-motion.js keys its animations off data-vh-widget.
  • Per-user layout — stored in user meta vulnhub_dashboard_layout, with the ids a user has ever had in vulnhub_dashboard_seen. It is sanitised on save (unknown ids and duplicates dropped, widths snapped), whether saved by drag (POST vulnhub-dashboard/v1/layout), by the Customise panel's Save (admin-post.php?action=vulnhub_save_layout), or reset (/layout/reset). Customise needs JavaScript; without it the board still renders from the saved layout. A user can never store a widget they can't see.
  • CSV export — served from a nonced admin-post.php endpoint (vulnhub_widget_csv), gated by Caps::VIEW, straight from your data callback.

"Copy as TSV" copies the first <table> in the widget, not the data callback. A widget that draws no table gets a copy button with nothing to copy, so render a table view (even a visually hidden one) if you want that button to work.

The cache — read this before you wonder why a change didn't show

Rendered widget HTML is cached in a transient keyed vh_w_<md5(id|locale|home_url)> (the host is in the key because widget HTML carries absolute links and this app answers on two hostnames). There are two horizons: 15-minute freshness and 6-hour serve-stale. On render the board serves the cached copy immediately and, if stale, queues a background re-render — so a sync never makes a visitor wait.

Invalidation is by epoch stamp travelling inside the cache entry ({html, epoch, fresh_until}), not in the key — so a bust marks markup stale rather than hiding it. Each widget's stamp is composed from its depends sources plus a global floor. When a connector finishes, bust_for_connector() maps it to the sources it moved and ticks only those, so only the affected widgets rebuild. The map is filterable via vulnhub_widget_connector_sources:

An unknown connector busts everything. (No core widget currently declares threat; the attack-path widget declares no depends, so it rebuilds on every bust.)

Rebuilding happens off the request path. A stale read queues vulnhub_widget_refresh for that one widget (5-minute lock). After vulnhub_sync_complete or vulnhub_coverage_recalculated, queue_warm() (2-minute lock) re-renders the default layout plus the ids on up to 200 users' boards, for every remembered host (up to 4). An hourly vulnhub_widget_warm_cron does the same as a safety net. warm_state() reports the last warm's time, count and epoch, and vulnhub_widget_cache_ttl / vulnhub_widget_stale_ttl tune the two horizons.

Consequence for development and content edits: editing a widget's PHP does not change what visitors see until its cache entry rolls or is busted. To mark every widget stale without deleting anything, run wp eval 'VulnHub_Dash_Widgets::bust();' — the next viewer still gets the old markup while a refresh is queued. wp cache flush deletes the entries (Redis holds the transients), so the next viewer renders them fresh. Saving platform Settings also calls bust(). In production, a connector sync busts the right widgets automatically.

A finished CSV import busts the board twice over: vulnhub_import_complete now fires when the job completes, and the import runner's own Coverage::recalculate() fires vulnhub_coverage_recalculated. That is harmless — a bust only ticks an epoch, and the warm job holds a two-minute lock.

A note on live vs cached data

Most widgets run their SQL live on each (uncached) render, so freshness tracks the last sync. Two add their own caching — Exposure by product (a live aggregate cached in a vh_prod_… transient for 6 hours, invalidated by any bust because the global epoch is part of its key) and Patch availability (a per-request memo). A materialised product summary table exists in the schema, but its rebuild routine is not currently called, so that path never serves. The trend widget is special: it reads a pre-aggregated nightly snapshot table, not live findings, because it is plotting history.
