VulnHub carries several different scores, and they answer different questions. Severity is how bad the bug is; KEV, EPSS and exploit references are how likely it is to be used; VPR and the risk score blend those with how much the affected machine matters to you. Reading them as one number is the most common way to mis-prioritise, so this page keeps them apart.

Severity

Severity is the familiar five-rung ladder. It comes straight from the scanner (Tenable) as a category, and severity_id maps one-to-one to Tenable's numeric ids:

Labelseverity_idRisk weight
Critical440
High320
Medium28
Low13
Info00

Severity is a categorical label, not a recomputation of the raw CVSS score. The underlying scores are stored separately on each definition (cvss2_base, cvss3_base, vpr_score) and feed the risk score, not the severity bucket.

Info findings are suppressed, not deleted. Informational findings (severity Info) are parked in the suppressed state and sit outside every count on every screen. They are still in the database — some of them (the Netstat port-scanner plugins) are exactly what the reachability engine reads — but they never inflate a number a person is meant to act on.

Is it exploitable? Three independent signals

"Exploitable today" is not a single vendor's opinion — it is built from three free, public, unauthenticated feeds, refreshed nightly. None of your estate data ever leaves the box to get them.

KEVCISA Known Exploited Vulnerabilities. The authoritative "this is being exploited in the wild right now" list. The highest-trust signal. Also carries whether the CVE is used in ransomware campaigns.
EPSSFIRST Exploit Prediction Scoring System. A daily-updated probability (0–1) that a CVE will be exploited in the next 30 days, plus a percentile ranking it against all CVEs.
exploit_refsPublished exploit code. A count of NVD references tagged "Exploit" — pointers to working proof-of-concept or weaponised code.

The EPSS threshold

EPSS is a continuous probability, so it needs a line. A CVE counts as "likely enough to matter" when its EPSS is at or above the threshold, which defaults to 0.10 (a 10% chance in the next 30 days). Administrators can change it under Settings (option vulnhub_threat_epss_min); changing it re-derives the flags in a single SQL statement, with no need to re-ingest the feeds.

How the three combine into has_poc

A CVE is flagged has_poc = 1 ("a working exploit is plausible") when any enabled source fires:

has_poc = ( kev = 1  OR  exploit_refs > 0  OR  epss >= threshold )

Which sources are enabled is configurable (default: all three — kev, refs, epss). A scanner definition is flagged exploitable if any of its CVEs is. This has_poc flag — rolled up onto the poc_route — is exactly what the "How an attacker gets in" widget means by counting only exploitable findings.

Which evidence is shown, when several apply

When a finding qualifies on more than one signal, VulnHub shows the most defensible one, not the highest-scoring. The order is: KEV (known-exploited) beats a published exploit reference beats being over the EPSS threshold; ties break on the higher EPSS. So "on CISA's exploited list" is always shown in preference to "has an 18% EPSS", because the first is an observation and the second is a prediction.

VPR and the risk score

VPR (Vulnerability Priority Rating) is Tenable's own 0–10 priority number, blending CVSS with threat intelligence. VulnHub stores it on the definition (vpr_score) straight from the Tenable import — it is a feed value, not something VulnHub computes, and it does not feed the has_poc exploitability flag. It feeds the risk score.

The risk score is VulnHub's single prioritisation number for a finding, capped at 100. It combines four things:

risk = severity_weight
     × criticality_factor          // asset importance: critical 2.0, high 1.5, medium 1.0, low 0.6
     × (exploitable ? 1.4 : 1.0)   // a working exploit raises it 40%
     × (1 + VPR / 20)              // Tenable's priority nudges it, when present
     (then capped at 100)

The asset-classification rules can nudge this further: a rule that sets a machine's priority weight multiplies the risk of every finding on it (200 doubles it, 50 halves it). This is how "the same CVE on a crown-jewel database server outranks it on a spare laptop" is expressed as a number.

Rule of thumb for prioritising. Start with the attack-path widget (what a stranger can reach), then within a lane sort by risk score — it already folds in severity, whether an exploit exists, Tenable's VPR, and how much the machine matters. Don't sort by raw CVSS alone; a 9.8 on an unreachable spare is not your first job.
